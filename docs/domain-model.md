# ドメインモデル

VBAマクロブックが扱っている業務を、アプリケーションのデータモデルとして再構成したもの。
技術スタックに依存しない論理設計。

物理設計（DDL）は [design.md 8章](./design.md#8-テーブル定義主要部) を参照。

---

## 1. 業務構造

```
自社（レンタル会社）
  └─ 販売先 = 架空事務機株式会社（一次店・請求先は常にこの1社）
       └─ 納品先 = 建設現場（契約番号ごと・毎月数十〜百数十件）
            └─ 明細行（品番・数量・単価・期間）
```

請求書は**1社宛て1通**、その裏付けとして**現場ごとの請求明細書が数十枚**つく。
この親子構造がモデルの骨格になる。

---

## 2. 確定している前提

実データ（937行 × 49列）のプロファイリングから確定した事項。

### 販売先は1社のみ

937行すべての `販売先名称` が同一。請求書は税率ごとに1通（10%用・8%用）、
請求明細書は契約 × 納品先ごとに1枚以上。

→ 請求書と請求明細書は別エンティティ。合計は明細書側からの積み上げ。

### 8% は軽減税率。品番 `ＳＲ－ＷＰＥＴ`（飲料水）だけが対象

VBAは品番の完全一致で判定し、10%側では同じ品番を除外している。相互排他。

→ 品番のハードコードを廃し、品目マスタの `tax_category` に持たせる。税制改定に耐える。

### 品番に `ＰＣＡ` を含むもの（カウンタ類）は別の明細書に分ける

同一契約でも備品とカウンタで明細書が分かれ、納品先名に `　カウンタ` が付く。
VBAではこれが分岐②③として実装され、コード重複の主因になっている。

→ 品目マスタの `billing_group` で表現。分岐ではなくグルーピングのキーになる。

### 品名に「値引」を含む行は請求対象外

実データでは10行・合計 −74,977円。VBAは明細書に転記せず、請求額にも反映しない。
**業務上これが正しい扱いとして確定済み。**

→ 明細行に `is_billable` を持ち、請求対象外の行もデータとしては保持する（監査可能性のため捨てない）。

### 単価は3系統で完全に排他

| 種別 | 行数 |
|---|---|
| 月単価のみ | 52 |
| 日単価のみ | 817 |
| 販売単価のみ | 68 |
| 複数あり | **0** |
| すべて欠損 | **0** |

VBAの優先順位分岐（月 → 日 → 販売）はデータ的に裏づけられている。

→ 3列を `unit_price` ＋ `unit_price_type` の2列に畳める。**分岐がデータになる好例。**

## 3. エンティティ関連

```
customer (販売先) ──┐
                    ├──< contract (契約) >── site (現場) ──> client (得意先)
sales_rep ──────────┘         │
                              │
                              └──< rental_order (受注) ──< billing_line (明細行) >── item (品目)
                                                                  │
billing_period (請求期間) ────────────────────────────────────────┤
        │                                                         │
        └──< invoice (請求書) ──< invoice_statement (請求明細書) >─┘
```

| 層 | エンティティ | 性質 |
|---|---|---|
| **マスタ** | `office` `customer` `client` `site` `sales_rep` `item` `contract` | 月次処理をまたいで存続 |
| **取引** | `billing_period` `rental_order` `billing_line` | 請求期間ごとに取り込まれる |
| **出力** | `invoice` `invoice_statement` `issued_document` | 生成される帳票 |

### この構造の要点

VBAが「44行オフセット」で表現していた紙面構造が、
`invoice → invoice_statement → billing_line` という3階層の親子関係に置き換わる。

**ページ数・改ページ位置・書き込み行といった概念はモデルから完全に消え**、
出力層（PDF生成）だけの関心事になる。

## 4. 主要な設計判断

### 明細行にはサロゲートキーが必須

元データに自然キーが存在しない。

| キー候補 | ユニーク数 | 判定 |
|---|---|---|
| 識別番号 | 851 / 937 | 重複あり（79種・165行） |
| 識別番号 + 受注番号 | 907 / 937 | 重複あり |
| 契約番号 + 品番 + 納品日 + 小計 | 920 / 937 | 重複あり |

同一内容の行が正当に複数存在する（同じ機材を同条件で複数台、別受注で借りているケース）。

```
既存: 契約7000000000005 / DM-031 / 3/8納品 / 1,488円
新規: 契約7000000000005 / DM-031 / 3/8納品 / 1,488円
                                    ↑
              「同じ行」か「別の2台目」か、データからは区別できない
```

→ **差分更新は原理的に不可能。洗い替え方式を採用する理由がこれ。**

### 契約はマスタ化できる

| 属性 | 契約あたりの種類数 | 判定 |
|---|---|---|
| 納品先名称 | 最大 1 | 1:1 |
| 住所 | 最大 1 | 1:1 |
| 販売先名称 | 最大 1 | 1:1 |
| 初回納品日 | 最大 12 | **1:N** → 明細行の属性 |

納品先 → 契約は 1:N（1納品先に契約2件のケースが1組）。
そのため `site` は `contract` と別エンティティにする。

### 受注は中間エンティティとして実在する

1受注に最大27明細。`受注番号` → `納品先名称` は 1:1 だが、`品番` は 1:N。

### 品名は明細行にスナップショットする

元データでは品番 → 品名は 1:1 だが、マスタの改称に過去の請求書が引きずられてはいけない。
発行時点の名称を `billing_line.item_name_snapshot` に凍結する。

## 5. 元データ49列の行き先

| # | 元の列 | 扱い | 行き先・理由 |
|---|---|---|---|
| 1 | 識別番号 | 採用 | `billing_line.source_key`（追跡用。一意ではない） |
| 2–3 | 受注営業所コード／名 | 採用 | `office`。実データは1拠点のみ |
| 4–5 | 販売先コード／名称 | 採用 | `customer` |
| 6 | 販売先担当者 | 採用 | `customer.contact_name` |
| 7–8 | 営業担当者コード／名 | 採用 | `sales_rep` |
| 9 | 住所 | 採用 | `site.address` |
| 10 | 受注番号 | 採用 | `rental_order.order_no`。1受注に最大27明細 |
| 11 | 契約番号 | 採用 | `contract.contract_no` |
| 12 | 初回納品日 | 採用 | `billing_line.delivery_date`。契約内で最大12種あり、行の属性 |
| 13 | 引取日 | 採用 | `billing_line.return_date`。欠損90% |
| 14–15 | 取引先発注番号1–2 | 採用 | `rental_order.po_number_1/2` |
| 16–18 | 取引先発注番号3–5 | **破棄** | 全937行が空 |
| 19 | 納品先名称 | 採用 | `site.name`。会社名は名寄せして `site.client_id` へ |
| 20 | 納品日 | 採用 | `billing_line.shipped_date` |
| 21–22 | 品番／品名 | 採用 | `item` ＋ 明細行にスナップショット |
| 23 | 明細数量 | 採用 | `billing_line.quantity` |
| 24 | 商品摘要 | 採用 | `billing_line.note`。欠損86% |
| 25–26 | レンタル開始／終了日 | 採用 | `billing_line.rental_start / rental_end` |
| 27 | レンタル期間 | **導出** | 終了日 − 開始日 |
| 28–29 | 請求期間開始／終了日 | 採用 | `billing_period` に正規化（全行同値） |
| 30–31 | 経過日数／月換算 | 採用 | `billing_line.duration` に統合 |
| 32 | 単位 | 採用 | `billing_line.unit` |
| 33 | 備考 | **破棄** | 「契約番号＋レンタル」の機械生成文字列 |
| 34 | 基本料 | 採用 | `billing_line.base_charge`。0 は NULL 扱い |
| 35–37 | 月単価／日単価／販売単価 | 採用 | `unit_price` ＋ `unit_price_type` の2列に統合 |
| 38 | レンタル単価 | **導出** | 月単価または日単価の写し |
| 39–40 | レンタル金額／販売金額 | **導出** | 単価 × 数量 × 期間 |
| 41 | 小計 | 採用 | `billing_line.amount`。**VBAが実際に使う唯一の金額列** |
| 42 | 合計 | **導出** | 契約単位の集計 |
| 43–44 | 二桁値引後計／二桁値引 | **破棄** | VBA未参照・業務でも不使用と確認済み |
| 45–46 | 表示順／順番 | 採用 | `billing_line.display_order / seq` |
| 47 | 再発行 | 採用 | 列は空だが概念は活かす → `invoice.revision` |
| 48 | 削除 | 採用 | → `billing_line.deleted_at`（論理削除） |
| 49 | 暫定区分 | 採用 | → `billing_line.is_provisional` |

**採用 34列相当 / 導出 6列 / 破棄 9列。**
導出列を持たないことで、金額の整合性は常に計算で保証される。

## 6. VBA処理との対応

移植時の受け入れ基準になる対応表。

| VBAの処理 | 行数 | アプリでの実装 |
|---|---|---|
| `リスト表作成()` | 約260 | 取込時に `contract` をUPSERT。一覧は検索クエリ |
| `CreateCompanyList()` | 約120 | 納品先名の正規化を**取引先マスタ＋表記ゆれ辞書**へ |
| `請求明細書出力10()` | 約1,600 | `GROUP BY contract, billing_group` ＋ HTML/CSSでページ組み |
| `請求明細書出力8()` | 約670 | **上と同一処理。** `tax_category` を引数に取るだけ |
| `請求書10/8_請求明細から抽出()` | 約540 | `SUM(statement.total_ex_tax)`。明細を真実とする思想は継承 |
| `明細数の確認()` | 約60 | **発行前バリデーション**として本格化 |
| `リスト表と営業データの差分()` | 約120 | 前月請求との差分ビュー |
| `CreatePDFOfBill()` | 約40 | HTML → PDF。会社ごと分割・自動命名 |
| 44行オフセット計算全般 | — | **消滅。** `page-break-inside: avoid` に置き換わる |
| `Bill8.bas` / `Bill10.bas` | 約1,300 | **移植対象外**（死にコード。一括処理から呼ばれていない） |
